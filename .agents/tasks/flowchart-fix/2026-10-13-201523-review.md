# Compact flowchart generation and automatic cursor-click selection

This task replaced the file-by-file "emit one node per IR statement" approach with a detail-aware pipeline (`overview` / `standard` / `detailed`) and added a new `/api/flowchart/analyze/selection` endpoint that returns a sub-graph for whatever construct the cursor is sitting on. The client side wires cursor-move events in the Monaco editor through a 400 ms debounce to that endpoint, swapping the canvas to "Selection Mode" when a meaningful response arrives. All changes are additive on top of the existing IR pipeline; no existing routes, exports, or React props were removed.

Watch for: (**confirmed**) `trueBranch` / `falseBranch` are empty arrays in the JavaScript adapter's IR output for `if/else` blocks, so the YES/NO branch nodes are never emitted — the decision node connects to END on both edges with no visible branch content. This is a pre-existing adapter gap, but it directly undermines the professor-demo requirement of showing `[Pass]` and `[Fail]` nodes. (**confirmed**) `analyzeSelection` in `flowchartApi.ts` retains `err: any` in its catch block while all other functions in the same file were updated during the lint-fix pass — this is the sole remaining `any` escape in the new code paths.

**Verdict**: CHANGES_REQUESTED

---

## High-level view

The server-side compact mode works: 25 consecutive assignments collapse to a single `Statements (25)` node; a top-level `if/else` snippet produces 3 nodes (START → DECISION → END). The 80-node collapse threshold in `generateFlowchartFromIR` guards against runaway recursion into deep function bodies, and the LRU-style parse cache in `/analyze/selection` prevents re-parsing unchanged files on every cursor move. These are all confirmed working against the live server.

The selection endpoint exists, returns `{success:true, nodes, edges}`, and is registered in the `availableEndpoints` banner in `index.js`. `findSelectionContext` correctly prefers the innermost `function_def`, then `decision`/`loop`, then a ±5-line proximity fallback. For the tested snippet the fallback is the whole IR array (3 items), which is acceptable for small files.

The critical professor-demo case — an `if/else` with `console.log("Pass")` / `console.log("Fail")` in the true/false branches — produces a 3-node graph: START, DECISION (Check: marks>=40), END. Both YES and NO edges point directly to END with no branch body nodes, because the JavaScript adapter stores the branch bodies in `trueBranch: []` / `falseBranch: []`. `generateFlowchartFromIR` calls `translateSequence(item.trueBranch, ...)` and `translateSequence(item.falseBranch, ...)` on those empty arrays, producing no branch nodes. This is a pre-existing adapter limitation, but it is exactly the scenario the requirements diagram shows and it is not fixed here.

The client-side wiring is complete: `SelectionAnalysisParams` type, `analyzeSelection()` service function, debounced `useEffect` in `FlowchartPanel`, `onSelectionChange` prop on `CodeEditor`, and `cursorEndLine` state in `page.tsx`. The Selection Mode badge with its dismiss button renders inside the canvas area. The `analyzeSelection` catch block uses `err: any` — the only instance remaining in the new code paths after the lint-fix pass.

### Empty branch bodies in the JavaScript if/else IR

The requirements diagram shows the expected output for `if (marks >= 40) { console.log("Pass"); } else { console.log("Fail"); }` as START → decision diamond → YES: [Pass] / NO: [Fail] → END. Live testing against the server confirms the actual output is START → DECISION (Check: marks>=40) → END, with both YES and NO edges skipping directly to END. Inspecting the raw IR (`parseToIR` output):

```json
[{
  "type": "decision",
  "condition": "marks>=40",
  "trueBranch": [],
  "falseBranch": [],
  "lineStart": 1,
  "lineEnd": 1
}]
```

The `console.log` calls inside the branches are not appearing in the IR at all. `flowGenerator.js` is correct — it calls `translateSequence(item.trueBranch, ...)` — but it has nothing to translate. The fix must be in `server/analyzer/ast/javascriptAdapter.js`: the branch body extraction needs to walk the AST children of the if-consequent and if-alternate and produce `OUTPUT` IR nodes for `console.log` / `console.error` calls found there. FEAT-001's findings acknowledge this as pre-existing adapter behavior; this review flags it as a blocking gap for the stated professor-demo requirement.
